# Architecture Decision Record (ADR)

## Анализ шард-ключей для коллекций Black Friday

### 1. Коллекция `orders`

#### Атрибуты:

- `_id: ObjectId`
- `user_id: ObjectId`
- `items: { product_id: ObjectId, quantity: number, price: number }[]`
- `status: "active" | "ordered" | "abandoned"`
- `total: number`
- `geo_zone: string`
- `created_at: Date`

#### Кандидаты для шард-ключа:

**1. `geo_zone` (простой ключ)**

- **Преимущества:**
  - Распределение по географическим зонам
  - Отчётность и аналитика часто требуют данные по регионам
  - Хорошая кардинальность при достаточном количестве геозон
- **Недостатки:**
  - Потенциальная неравномерность нагрузки (Москва vs маленькие города)
  - При малом количестве зон - ограниченная масштабируемость

**2. `{ geo_zone: 1, user_id: 1 }` (составной ключ)**

- **Преимущества:**
  - Лучшая кардинальность за счёт комбинации полей
  - Эффективный поиск истории заказов конкретного пользователя
  - Сохраняется географическая локальность данных
  - Более равномерное распределение данных по шардам
- **Недостатки:**
  - Требует указания обоих полей в запросах для оптимальной производительности

**3. `user_id` (простой ключ, хешированный)**

- **Преимущества:**
  - Равномерное распределение данных
  - Быстрый поиск всех заказов пользователя
  - Простота использования
- **Недостатки:**
  - Полностью теряется географическая локальность

#### **Лучший кандидат:** `{ geo_zone: 1, user_id: 1 }`

---

### 2. Коллекция `products`

#### Атрибуты:

- `_id: ObjectId`
- `name: string`
- `category: string`
- `price: number`
- `amount_left: {geo_zone: string, amount: number}[]`
- `attributes: Object`

#### Кандидаты для шард-ключа:

**1. `category` (простой ключ)**

- **Преимущества:**
  - Естественная группировка данных
  - Эффективный поиск и фильтрация по категориям
  - Хорошо подходит для аналитики по категориям
- **Недостатки:**
  - Низкая кардинальность (ограниченное количество категорий)
  - Популярные категории ("Электроника") создадут hot-spot
  - Неравномерное распределение данных
  - Плохая масштабируемость

**2. `{ category: 1, _id: 1 }` (составной ключ)**

- **Преимущества:**
  - Высокая кардинальность за счёт добавления уникального \_id
  - Эффективный поиск по категориям
  - Равномерное распределение данных внутри категорий
  - Поддержка поиска конкретного товара по \_id с указанием категории
- **Недостатки:**
  - Поиск товара только по \_id потребует scatter-gather
  - Обновление остатков требует знания категории товара

**3. `_id` (простой ключ, хешированный)**

- **Преимущества:**
  - Максимально равномерное распределение
  - Быстрый доступ к конкретному товару по \_id
  - Хорошая масштабируемость
  - Простота реализации
- **Недостатки:**
  - Поиск по категориям всегда требует scatter-gather
  - Фильтрация по цене будет неэффективной
  - Нет географической локальности для обновления остатков

**4. `{ category: 1, price: 1 }` (составной ключ с range-полем)**

- **Преимущества:**
  - Оптимален для поиска по категориям с фильтрацией по цене
  - Эффективные range-запросы по цене внутри категории
- **Недостатки:**
  - Низкая общая кардинальность
  - Потенциальные hot-spots в популярных ценовых диапазонах
  - Изменение цены может потребовать миграции документа между шардами
  - Не рекомендуется использовать изменяемые поля в шард-ключе

#### **Лучший кандидат:** `{ category: 1, _id: 1 }`

Обеспечивает баланс между эффективным поиском по категориям и равномерным распределением данных.

Альтернатива: хешированный `_id` для максимальной производительности записи, если чтение по категориям менее критично.

### 3. Коллекция `carts`

#### Атрибуты:

- `_id: ObjectId`
- `user_id: ObjectId`
- `session_id: string`
- `items: { product_id: ObjectId, quantity: number }[]`
- `status: "active" | "ordered" | "abandoned"`
- `created_at: Date`
- `updated_at: Date`
- `expires_at: Date`

#### Кандидаты для шард-ключа:

**1. `session_id` (простой ключ, хешированный)**

- **Преимущества:**
  - Очень высокая кардинальность (уникальные сессии)
  - Равномерное распределение
  - Быстрый доступ к гостевым корзинам
  - Хорошая масштабируемость
- **Недостатки:**
  - Поиск корзины авторизованного пользователя по `user_id` требует scatter-gather
  - Операция слияния корзин может быть неэффективной
  - После авторизации пользователь чаще работает через `user_id`, а не `session_id`

**2. `user_id` (простой ключ, хешированный)**

- **Преимущества:**
  - Высокая кардинальность
  - Равномерное распределение
  - Эффективный поиск корзины авторизованного пользователя
  - Оптимально для постоянных клиентов
- **Недостатки:**
  - Гостевые корзины (без `user_id`) не могут использовать этот ключ
  - Требуется дополнительная логика для обработки гостей
  - Часть корзин может иметь null или временное значение `user_id`

**3. `_id` (простой ключ, хешированный)**

- **Преимущества:**
  - Максимально равномерное распределение
  - Простота реализации
  - Отличная масштабируемость
- **Недостатки:**
  - Поиск активной корзины по `user_id` или `session_id` всегда требует scatter-gather

**4. Гибридный подход: составной ключ `{ user_id: 1, session_id: 1 }`**

- **Преимущества:**
  - Покрывает оба сценария: авторизованные и гостевые корзины
  - Высокая кардинальность
  - Для авторизованных: поиск по `user_id`
  - Для гостей: поиск по `session_id`
- **Недостатки:**
  - Сложность реализации: нужно заполнять оба поля или использовать условную логику
  - Один из ключей часто будет null или пустым

#### **Лучший кандидат:**

Хешированный `user_id` для основной коллекции `carts`, где для гостевых корзин используется временный `user_id` (например, на основе `session_id`). При авторизации гостя происходит обновление `user_id` на реальный.

## Выбор стратегий шардирования

### 1. Коллекция `orders`

#### **Выбранная стратегия:** диапазонное шардирование

#### **Шард-ключ:** `{ geo_zone: 1, user_id: 1 }`

#### **Обоснование выбора:**

1. **Географическая локальность данных**

   - Заказы физически группируются по регионам
   - Списание остатков товаров происходит в рамках одной геозоны
   - Минимизируются межшардовые транзакции при оформлении заказа

   ```javascript
   // Создание заказа с списанием остатков
   // Все данные (заказ + остатки в геозоне) на одном или соседних шардах
   db.orders.insertOne({
     user_id: ObjectId("..."),
     geo_zone: "Moscow",
     items: [{ product_id: ObjectId("..."), quantity: 2 }],
   });

   // Обновление остатков в той же геозоне — локальная операция
   db.products.updateOne(
     { _id: product_id, "amount_left.geo_zone": "Moscow" },
     { $inc: { "amount_left.$.amount": -2 } }
   );
   ```

2. **Эффективные запросы для основных операций**

   **Операция 1: История заказов пользователя (15% трафика)**

   ```javascript
   // Targeted query — один шард
   db.orders.find({
     geo_zone: "Moscow",
     user_id: ObjectId("..."),
   });
   ```

   **Операция 2: Создание заказа (80% трафика)**

   ```javascript
   // Запись идёт точно в нужный шард
   db.orders.insertOne({
     geo_zone: "Moscow",      // ← Mongos сразу знает шард
     user_id: ObjectId("..."),
     items: [...],
     status: "active"
   })
   ```

   **Операция 3: Отчёты по геозоне (5% трафика)**

   ```javascript
   // Частичный scatter — только шарды одной геозоны
   db.orders.aggregate([
     { $match: { geo_zone: "Moscow" } },
     { $group: { _id: "$status", total: { $sum: "$total" } } },
   ]);
   ```

3. **Высокая кардинальность составного ключа**

   - `geo_zone`: 10-50 значений (основные города России)
   - `user_id`: миллионы значений
   - **Итоговая кардинальность**: очень высокая
   - Равномерное распределение внутри каждой геозоны

4. **Бизнес-логика Black Friday**
   - Пиковые нагрузки различаются по регионам (разные часовые пояса)
   - Москва: пик в 12:00 MSK → нагрузка на шарды Москвы
   - Владивосток: пик в 12:00 VLAT (9 часов разницы) → нагрузка на шарды Владивостока
   - **Естественное распределение нагрузки во времени**

---

#### **Почему не полное географическое распределение?**

**1. Межрегиональные операции**
Проблема: пользователь из Москвы покупает товар, но его остатки закончились в московской геозоне

При географическом распределении:

1. Запись заказа → Дата-центр Москвы (80ms latency внутри)
2. Списание остатков → Дата-центр СПб (150ms latency между городами!)
3. Обновление inventory → Дата-центр СПб (ещё 150ms)
   Итого: 380ms вместо 80ms

**2. Отсутствие строгой привязки пользователя к региону**
Пользователь из одного региона может делать заказ в другой.

**3. Высокие требования к инфраструктуре**

**4. Black Friday — это кратковременный пик**

Характеристики Black Friday:

- Длительность: 24-48 часов
- Основной пик: 00:00 - 06:00 (6 часов)
- Остальное время: обычная нагрузка

Географическое распределение оправдано для:

- Круглогодичной высокой нагрузки
- Строгих требований к latency (< 50ms)
- Юридических требований (хранение данных в регионе)

#### **Конфигурация шардирования:**

```javascript
// 1. Создание шардированной коллекции
sh.enableSharding("somedb");

// 2. Создание индекса для шард-ключа
db.orders.createIndex({ geo_zone: 1, user_id: 1 });

// 3. Шардирование коллекции
sh.shardCollection("somedb.orders", { geo_zone: 1, user_id: 1 });

// 4. Предварительное разделение на зоны (Zone Sharding)
// Распределяем геозоны по шардам для контроля

// Москва и область → Shard 0, 1
sh.addShardToZone("shard0", "moscow-zone");
sh.addShardToZone("shard1", "moscow-zone");
sh.updateZoneKeyRange(
  "somedb.orders",
  { geo_zone: "Moscow", user_id: MinKey },
  { geo_zone: "Moscow", user_id: MaxKey },
  "moscow-zone"
);

// Санкт-Петербург → Shard 2
sh.addShardToZone("shard2", "spb-zone");
sh.updateZoneKeyRange(
  "somedb.orders",
  { geo_zone: "SPB", user_id: MinKey },
  { geo_zone: "SPB", user_id: MaxKey },
  "spb-zone"
);

// Остальные регионы → Shard 3, 4
sh.addShardToZone("shard3", "other-zone");
sh.addShardToZone("shard4", "other-zone");
```

### 2. Коллекция `products`

#### **Выбранная стратегия:** диапазонное шардирование

#### **Шард-ключ:** `{ category: 1, _id: 1 }`

#### **Обоснование выбора:**

1. **Основной паттерн использования — поиск по категориям**

   **Операция 1: Каталог товаров**

   ```javascript
   // Targeted query — только шарды с данной категорией
   db.products
     .find({
       category: "Electronics",
       price: { $gte: 10000, $lte: 50000 },
     })
     .sort({ price: 1 });

   // Mongos направляет запрос только на шарды с "Electronics"
   // Например: Shard 1 и Shard 2 (если категория распределена на 2 шарда)
   ```

2. **Равномерное распределение через \_id**

   - Проблема: категорий мало (~20-50), популярные категории создадут hot-spots
   - Решение: добавление `_id` как второй части ключа
   - Внутри каждой категории товары равномерно распределяются по ObjectId

   ```javascript
   // Распределение товаров категории "Electronics"
   Shard 1: { category: "Electronics", _id: ObjectId("507f1f...") ... ObjectId("607f1f...") }
   Shard 2: { category: "Electronics", _id: ObjectId("607f1f...") ... ObjectId("707f1f...") }
   Shard 3: { category: "Electronics", _id: ObjectId("707f1f...") ... ObjectId("807f1f...") }

   // Категория "Books" может быть меньше
   Shard 4: { category: "Books", _id: ObjectId("507f1f...") ... ObjectId("807f1f...") }
   ```

3. **Эффективное обновление остатков**

   **Операция 2: Списание товара**

   ```javascript
   // Если знаем category и _id — прямое попадание в один шард
   db.products.updateOne(
     {
       category: "Electronics", // ← из кеша или контекста заказа
       _id: ObjectId("507f1f77bcf86cd799439011"),
     },
     {
       $inc: { "amount_left.$[elem].amount": -1 },
     },
     {
       arrayFilters: [{ "elem.geo_zone": "Moscow" }],
     }
   );
   ```

4. **Изоляция нагрузки по категориям**

#### **Конфигурация шардирования:**

```javascript
// 1. Создание индекса
db.products.createIndex({ category: 1, _id: 1 });

// 2. Шардирование
sh.shardCollection("somedb.products", { category: 1, _id: 1 });

// 3. Опционально: Zone Sharding для контроля популярных категорий
// Выделяем больше шардов для "Электроники"
sh.addShardToZone("shard0", "electronics-zone");
sh.addShardToZone("shard1", "electronics-zone");
sh.addShardToZone("shard2", "electronics-zone");

sh.updateZoneKeyRange(
  "somedb.products",
  { category: "Electronics", _id: MinKey },
  { category: "Electronics", _id: MaxKey },
  "electronics-zone"
);

// Остальные категории на других шардах
sh.addShardToZone("shard3", "other-categories");
sh.addShardToZone("shard4", "other-categories");
```

### 3. Коллекция `carts`

#### **Выбранная стратегия:** хэшированное шардирование

#### **Шард-ключ:** `user_id` (hashed)

#### **Обоснование выбора:**

1. **Максимально равномерное распределение нагрузки**

   **Black Friday характеристика:**

   - Огромное количество одновременных пользователей
   - Постоянные обновления корзин

2. **Эффективные операции с корзиной**

   **Операция 1: Получить активную корзину**

   ```javascript
   db.carts.findOne({
     user_id: ObjectId("507f1f77bcf86cd799439011"),
     status: "active",
   });

   // Hash(user_id) → Shard 2
   // Запрос идёт напрямую на Shard 2
   ```

   **Операция 2: Добавить товар в корзину**

   ```javascript
   // Targeted update — один шард
   db.carts.updateOne(
     {
       user_id: ObjectId("507f1f77bcf86cd799439011"),
       status: "active",
     },
     {
       $push: {
         items: { product_id: ObjectId("..."), quantity: 1 },
       },
       $set: { updated_at: new Date() },
     }
   );
   ```

   **Операция 3: Создать корзину**

   ```javascript
   // Запись в случайный шард
   db.carts.insertOne({
     user_id: ObjectId("..."), // Хешируется → любой шард
     session_id: "abc123",
     items: [],
     status: "active",
     created_at: new Date(),
   });
   ```

3. **Решение проблемы гостевых корзин**

   ```javascript
   // Для гостей: генерируем временный user_id из session_id
   function getCartUserId(sessionId, realUserId) {
     if (realUserId) {
       return realUserId; // Авторизованный пользователь
     }
     // Гость: создаём стабильный ObjectId из session_id
     return ObjectId(
       crypto.createHash("md5").update(sessionId).digest("hex").substring(0, 24)
     );
   }

   // Создание гостевой корзины
   const guestUserId = getCartUserId(sessionId, null);
   db.carts.insertOne({
     user_id: guestUserId, // Временный, но стабильный
     session_id: sessionId,
     items: [{ product_id: ObjectId("..."), quantity: 1 }],
     status: "active",
     is_guest: true,
   });

   // При авторизации: обновляем user_id
   ```

4. **Автоматическая очистка старых корзин**

   ```javascript
   // TTL индекс для автоматического удаления
   db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 });

   // При создании корзины
   db.carts.insertOne({
     user_id: ObjectId("..."),
     items: [],
     status: "active",
     created_at: new Date(),
     expires_at: new Date(Date.now() + 7 * 24 * 60 * 60 * 1000), // 7 дней
   });

   // MongoDB автоматически удалит через 7 дней
   // Работает на каждом шарде независимо
   ```

5. **Отсутствие hot-spots при пиковых нагрузках**
   - VIP-клиенты с большими корзинами
   - Боты и скрипты
   - Влиятельные пользователи
   - **Все равномерно распределены по хешу**

#### **Конфигурация шардирования:**

```javascript
// 1. Создание хешированного индекса
db.carts.createIndex({ user_id: "hashed" });

// 2. Шардирование с хешированием
sh.shardCollection("somedb.carts", { user_id: "hashed" });
```

## Мониторинг и устранение "горячих" шардов

### Проблема

Категория "Электроника" вызвала перегрузку одного из шардов, так как 70% запросов приходилось на товары этой категории. При использовании шард-ключа `{ category: 1, _id: 1 }` товары одной категории могут концентрироваться на ограниченном числе шардов, создавая hot-spots.

### 1. Метрики мониторинга шардов

#### 1.1. Метрики распределения данных

**Размер данных по шардам:**

```javascript
// Проверка размера данных на каждом шарде
db.adminCommand({ dbStats: 1 });

// Детальная информация по коллекции
db.products.stats();

// Распределение чанков
sh.status();

// Количество документов на каждом шарде
db.products.aggregate([{ $collStats: { storageStats: {} } }]);
```

**Ключевые показатели:**

- **Дисбаланс данных**: отклонение размера данных между шардами > 20%
- **Количество чанков на шарде**: неравномерное распределение чанков (>30% разница)
- **Размер чанка**: средний размер чанка > 256 MB (указывает на проблемы с разделением)

#### 1.2. Метрики производительности

**Нагрузка на операции чтения/записи:**

```javascript
// Статистика операций по шардам
db.serverStatus().opcounters;

// Детальная статистика по шарду
db.serverStatus().metrics.operation;

// Время выполнения запросов
db.currentOp({
  secs_running: { $gt: 1 },
});
```

**Ключевые показатели:**

- **Operations per second (OPS)**: дисбаланс > 50% между шардами
- **Query execution time**: p99 latency на горячем шарде в 2+ раза выше

## Стратегии чтения из replica set

### Допустимая задержка репликации

**Общие требования для Black Friday:**

- **Критичные операции**: задержка репликации < 100ms (primary)
- **Важные операции**: задержка репликации < 1 секунда (primaryPreferred)
- **Некритичные операции**: задержка репликации < 5 секунд (secondary/secondaryPreferred)
- **Аналитика**: задержка репликации < 30 секунд (secondary)

### Коллекция `products`

#### Операции чтения для `products`

| Операция                                         | Read Preference        | Допустимая задержка | Обоснование                                                                                 |
| ------------------------------------------------ | ---------------------- | ------------------- | ------------------------------------------------------------------------------------------- |
| Частые обновления остатков при покупках          | **primary**            | 0ms                 | Критично: списание остатков требует актуальных данных. Риск oversell при чтении с secondary |
| Поиск товаров по категориям и фильтрация по цене | **secondaryPreferred** | < 5 сек             | Некритично: каталог обновляется редко. Разгружает primary для write-операций                |
| Описание товара на странице продукта             | **primaryPreferred**   | < 1 сек             | Важно: пользователь принимает решение о покупке. Нужны актуальные цена и наличие            |

#### Обоснование для `products`:

**1. Частые обновления остатков при покупках**

**Почему primary:**

- **Критичность**: Списание остатков — транзакционная операция
- **Риск**: Чтение с secondary → может прочитать устаревший остаток → oversell
- **Частота обновлений**: На Black Friday остатки меняются каждую секунду
- **Консистентность**: Требуется strong consistency (read-your-writes)

**Бизнес-риски при чтении с secondary:**

- Продажа товара с нулевым остатком → возврат, репутационные потери
- Финансовые потери при массовом oversell во время Black Friday

---

**2. Поиск товаров по категориям и фильтрация по цене**

**Почему secondaryPreferred:**

- **Некритичность**: Каталог — это справочная информация
- **Частота обновлений**: Характеристики товаров меняются редко (часы/дни)
- **Преимущество**: Разгружает primary для критичных write-операций
- **Допустимость lag**: Если новый товар появился или цена изменилась, пользователь увидит через 5 секунд — это приемлемо

**Обоснование:**

- На Black Friday каталог просматривают миллионы пользователей одновременно
- Эти запросы создают огромную нагрузку
- Вынос на secondary освобождает ресурсы primary для критичных операций (покупки, списание остатков)

---

**3. Описание товара на странице продукта**

**Почему primaryPreferred:**

- **Важность**: Страница продукта — это шаг перед покупкой, последний момент принятия решения
- **Актуальность данных**: Цена и наличие должны быть максимально свежими
- **Бизнес-логика**: Пользователь принимает решение о покупке на основе этой страницы
- **UX**: Лучше показать актуальную цену сразу, чем менять её при добавлении в корзину
- **Fallback на secondary**: При экстремальной перегрузке primary можем прочитать с secondary (лучше чем timeout)

**Обоснование:**

- Показываем максимально актуальные цены и остатки
- Снижаем риск негативного опыта (когда цена меняется между просмотром и добавлением в корзину)
- Primary справляется с нагрузкой, так как это targeted read (один документ по \_id)
- При экстремальной нагрузке (Black Friday) fallback на secondary защищает от полного отказа

---

### Коллекция `orders`

#### Операции чтения для `orders`

| Операция                                                             | Read Preference        | Допустимая задержка | Обоснование                                                                                         |
| -------------------------------------------------------------------- | ---------------------- | ------------------- | --------------------------------------------------------------------------------------------------- |
| Быстрое создание заказов с одновременным списанием остатков (чтение) | **primary**            | 0ms                 | Критично: транзакция требует strong consistency. Read-your-writes для подтверждения создания заказа |
| Поиск истории заказов конкретного пользователя                       | **secondaryPreferred** | < 5 сек             | Некритично: Историческая информация, чаще всего не требует большой точности                         |
| Отображение статуса заказа                                           | **primaryPreferred**   | < 1 сек             | Важно: пользователь должен видеть актуальный статус, особенно для активных заказов                  |

#### Обоснование для `orders`:

**1. Быстрое создание заказов с одновременным списанием остатков**

**Почему primary:**

- **Транзакционность**: Создание заказа + списание остатков — это атомарная операция
- **Read-your-writes**: Пользователь создал заказ → сразу редиректится на страницу "Ваш заказ"
- **Риск**: Если прочитаем с secondary, можем не увидеть только что созданный заказ → "Заказ не найден" → паника пользователя
- **Консистентность**: Требуется гарантия, что заказ действительно создан перед отображением

---

**2. Поиск истории заказов конкретного пользователя**

**Почему secondaryPreferred:**

- **Историческая информация**: История заказов — справочная информация, не требует абсолютной актуальности
- **Частота запросов**: Пользователи часто просматривают историю, это создаёт нагрузку
- **Разгрузка primary**: Primary должен обрабатывать критичные операции (создание новых заказов)
- **Fallback на primary**: Если secondary недоступны, прочитаем с primary

**Обоснование:**

- Старые заказы уже завершены и не меняются
- Eventual consistency приемлема для просмотра истории
- Задержка 2-5 секунд в отображении последних изменений статуса не критична
- Для только что созданных заказов используется отдельная операция с primary (read-your-writes)

---

**3. Отображение статуса заказа**

**Почему primaryPreferred:**

- **Актуальность**: Статус заказа — критичная информация для пользователя
- **Частота обновлений**: На Black Friday статус может меняться каждые 10-30 секунд (Создан → Оплачен → В обработке → Отправлен → Доставлен)
- **UX**: Пользователь постоянно обновляет страницу, ожидая изменения статуса
- **Fallback**: При перегрузке primary можем прочитать с secondary

**Обоснование primaryPreferred (а не primary):**

- **Балансировка**: Миллионы пользователей одновременно проверяют статусы
- **Допустимость**: Если статус изменился 2 секунды назад, но пользователь видит старый — это не катастрофа
- **Защита primary**: При экстремальной нагрузке fallback на secondary защищает от полного падения
- **Критичные случаи**: При необходимости (например, перед возвратом денег) всё равно прочитаем с primary явно

### Коллекция `carts`

#### Операции чтения для `carts`

| Операция                                                     | Read Preference      | Допустимый lag | Обоснование                                                                       |
| ------------------------------------------------------------ | -------------------- | -------------- | --------------------------------------------------------------------------------- |
| Создание корзины (чтение после создания)                     | **primary**          | 0ms            | Критично: после создания нужно сразу вернуть корзину пользователю                 |
| Получение текущей корзины по session_id или user_id          | **primaryPreferred** | < 1 сек        | Важно: корзина может обновляться из разных вкладок/устройств, нужны свежие данные |
| Добавление или замена товара в корзине (чтение после записи) | **primary**          | 0ms            | Критично: пользователь только что добавил товар и должен увидеть его немедленно   |
| Удаление товара из корзины (чтение после записи)             | **primary**          | 0ms            | Критично: пользователь удалил товар, не должен его видеть в корзине               |
| Слияние гостевой и пользовательской корзины (все чтения)     | **primary**          | 0ms            | Критично: транзакционная операция, требует strong consistency для всех шагов      |
| Отметка корзины как заказанной (чтение для проверки)         | **primary**          | 0ms            | Критично: перед финальным шагом нужны точные данные (цены могли измениться)       |

#### Обоснование для `carts`:

**1. Создание корзины**

**Почему primary:**

- **Read-your-writes**: После создания корзины сразу возвращаем её пользователю
- **Первое впечатление**: Гость/новый пользователь должен сразу увидеть работающую корзину
- **Риск**: Если прочитаем с secondary - "Корзина не найдена" сразу после создания - сломанный UX

---

**2. Получение текущей корзины**

**Почему primaryPreferred:**

- **Актуальность**: Пользователь может открыть несколько вкладок, работать с мобильного приложения
- **Синхронизация**: Изменения в одной вкладке должны быть видны в другой
- **Частота**: Корзина запрашивается при каждом переходе между страницами
- **Fallback**: При высокой нагрузке можем прочитать с secondary (лучше чем timeout)

**Обоснование primaryPreferred (а не primary):**

- **Масштаб**: Миллионы одновременных запросов корзин
- **Допустимость**: Если товар добавлен 1-2 секунды назад, но не виден → пользователь просто обновит страницу
- **Защита**: Fallback на secondary защищает от полного падения при экстремальной нагрузке

---

**3. Добавление/замена товара в корзине**

**Почему primary:**

- **Read-your-writes**: Пользователь нажал "Добавить в корзину" → должен сразу увидеть товар
- **Критичность для конверсии**: Это ключевой момент покупки
- **Риск**: Если товар не появился, пользователь может подумать, что сайт сломался, и уйти
- **Black Friday**: Пользователи нервничают, любая задержка снижает конверсию

**Бизнес-риски при чтении с secondary:**

- Пользователь добавил товар, secondary отстаёт на 3 секунды
- Пользователь видит пустую корзину
- Думает, что товар не добавился
- Добавляет ещё раз, товар дублируется
- Пользователь недоволен

---

**4. Удаление товара из корзины**

**Почему primary:**

- **Read-your-writes**: Пользователь не должен видеть товар после удаления
- **UX**: Если товар продолжает отображаться - пользователь недоволен

---

**5. Слияние гостевой и пользовательской корзины**

**Почему primary:**

- **Атомарность**: Все шаги должны выполниться целиком или откатиться
- **Критичность**: Пользователь не должен потерять товары при логине
- **Сложность**: Многоступенчатая операция требует консистентности

---

**6. Отметка корзины как заказанной**

**Почему primary:**

- **Критический момент**: Это последний шаг перед оплатой
- **Финальная проверка**: Нужны актуальные цены и наличие товаров
- **Риск**: Если прочитаем устаревшие данные, возможна оплата по старым ценам или за недоступные товары

**Критичность всех чтений в PRIMARY:**

- **Цены**: Могли измениться за последние секунды
- **Финансовые риски**: Продажа по неправильной цене или недоступного товара

## Миграция на Cassandra: модель данных, стратегии репликации и шардирования

## Анализ данных интернет-магазина

### 1. **orders**: MongoDB

**Почему MongoDB:**

- Транзакции обеспечивают атомарность: заказ создаётся только если товар в наличии
- Риск oversell при eventual consistency неприемлем
- Сложные запросы для аналитики (агрегации по статусам, регионам, периодам)
- Read-your-writes критичен: пользователь должен сразу увидеть свой заказ

**Почему НЕ Cassandra:**

- Eventual consistency - риск двойного списания или продажи недоступного товара
- Ограниченная поддержка транзакций

**Решение:** **MongoDB с оптимизированным шардированием**

---

### 2. **products**: MongoDB

**Почему MongoDB:**

- Критично: предотвращение oversell требует strong consistency
- Атомарные обновления `amount_left` с гарантией консистентности
- Индексы для быстрого поиска по категориям, цене, атрибутам
- Возможность complex queries (фильтрация, сортировка, агрегации)

**Почему не Cassandra:**

- Eventual consistency - множественные oversell на Black Friday
- Счётчики в Cassandra не гарантируют точность при высокой нагрузке
- Ограниченные возможности для поиска по вторичным атрибутам

**Решение:** **MongoDB** (с read preference optimization: каталог на secondary, покупки на primary)

---

### 3. **carts**: MongoDB для активных, Cassandra для брошенных

#### Активные корзины (status: "active"): **MongoDB**

**Почему MongoDB для активных:**

- Read-your-writes критичен: пользователь должен сразу видеть добавленный товар
- Транзакции для слияния гостевой и пользовательской корзины
- Быстрый поиск по user_id или session_id с индексами
- TTL индексы для автоматической очистки

---

#### Брошенные корзины (status: "abandoned"): Cassandra

**Почему Cassandra для брошенных:**

- Eventual consistency приемлема (это историческая аналитика)
- Высокая скорость записи (миллионы write/sec без bottleneck)
- Отличное сжатие для больших объёмов данных
- Time-series данные (abandoned_at) идеально подходят для Cassandra

**Схема данных:**

```cql
CREATE TABLE abandoned_carts (
    user_id UUID,
    abandoned_date DATE,
    cart_id UUID,
    items LIST<FROZEN<cart_item>>,
    total_value DECIMAL,
    abandoned_at TIMESTAMP,
    PRIMARY KEY ((user_id, abandoned_date), abandoned_at)
) WITH CLUSTERING ORDER BY (abandoned_at DESC);
```

**Решение:** **Гибридная архитектура**

- MongoDB для активных корзин
- Cassandra для брошенных корзин
- Переход: при смене статуса `active` → `abandoned` копируем в Cassandra, удаляем из MongoDB

---

### 4. **order_history**: Cassandra

**Почему Cassandra:**

- Time-series данные — сильная сторона Cassandra
- Eventual consistency приемлема (история не меняется)
- Отличное сжатие и хранение больших объёмов
- Быстрый поиск по partition key (user_id + период)
- Простые запросы

**Схема данных:**

```cql
CREATE TABLE order_history (
    user_id UUID,
    year_month INT,
    order_id UUID,
    created_at TIMESTAMP,
    status TEXT,
    total DECIMAL,
    items LIST<FROZEN<order_item>>,
    PRIMARY KEY ((user_id, year_month), created_at)
) WITH CLUSTERING ORDER BY (created_at DESC)
  AND compaction = {'class': 'TimeWindowCompactionStrategy'};
```

**Преимущества:**

- Партиционирование по (user_id, year_month) обеспечивает равномерное распределение
- Clustering по created_at позволяет быстро получить последние заказы
- Time-window compaction оптимизирован для time-series данных

### 5. **user_sessions**: Cassandra

**Почему Cassandra:**

- Eventual consistency приемлема (сессии — временные данные)
- Очень высокая скорость записи (миллионы write/sec)
- Встроенный TTL на уровне столбцов
- Leaderless репликация: нет bottleneck на записи
- Отличная производительность для key-value паттерна

**Схема данных:**

```cql
CREATE TABLE user_sessions (
    session_id UUID PRIMARY KEY,
    user_id UUID,
    created_at TIMESTAMP,
    last_activity TIMESTAMP,
    data MAP<TEXT, TEXT>,
    ip_address TEXT
) WITH default_time_to_live = 1800;  -- 30 минут TTL
```

## Детальная модель данных Cassandra

В Cassandra:

1. **Denormalization is normal** — дублирование данных для оптимизации запросов
2. **One table per query pattern** — каждый тип запроса - отдельная таблица
3. **Partition key is king** — все запросы должны включать partition key

---

### 1. История заказов (order_history)

#### Модель данных:

```cql
CREATE TABLE order_history (
    -- Partition Key
    user_id UUID,
    year_month INT,

    -- Clustering Columns
    created_at TIMESTAMP,
    order_id UUID,

    -- Data Columns
    status TEXT,
    total DECIMAL,
    geo_zone TEXT,
    items LIST<FROZEN<order_item>>,
    payment_method TEXT,
    delivery_address TEXT,

    PRIMARY KEY ((user_id, year_month), created_at, order_id)
) WITH CLUSTERING ORDER BY (created_at DESC, order_id ASC)
  AND compaction = {'class': 'TimeWindowCompactionStrategy',
                    'compaction_window_size': '30',
                    'compaction_window_unit': 'DAYS'}
  AND gc_grace_seconds = 864000;  -- 10 дней
```

#### Обоснование выбора ключей:

**Partition Key: (user_id, year_month)**

**Преимущества:**

- **Равномерное распределение**: каждый пользователь × месяц = уникальная партиция
- **Предсказуемый размер партиции**: ~30-50 заказов/месяц на пользователя = ~100-200 KB
- **Нет горячих партиций**: даже VIP-клиенты не создадут > 1000 заказов/месяц
- **Эффективный range scan**: запрос "заказы за год" = 12 партиций

**Clustering Key: (created_at DESC, order_id ASC)**

**Преимущества:**

- **Сортировка**: последние заказы первыми (типовой запрос)
- **Уникальность**: order_id гарантирует уникальность даже при одинаковом timestamp

## Стратегии обеспечения консистентности

### 1. order_history

#### **Read Repair + Periodic Anti-Entropy**

**Обоснование:**

**Read Repair:**

- **Когда**: При чтении истории заказов, это частая операция
- **Преимущество**: Низкая latency для пользователя
- **Компромисс**: Eventual consistency, но история не критична

**Anti-Entropy Repair:**

- **Когда**: Раз в неделю
- **Преимущество**: Гарантия согласованности
- **Компромисс**: Ресурсоёмкая операция

---

### 2. abandoned_carts

#### Выбранная стратегия: **Hinted Handoff**

**Обоснование:**

- **Когда**: Узел временно недоступен
- **Преимущество**: Исторические данные, их необязательно восстанавливать сразу же (поэтому не Read Repair)
- **Компромисс**: Temporary inconsistency (до 3 часов)

---

### 3. user_sessions

#### Выбранная стратегия: **Hinted Handoff + Read Repair**

**Обоснование:**

**Hinted Handoff:**

- **Когда**: Узел временно недоступен
- **Преимущество**: Если узел упал, writes продолжают работать. **Availability важнее consistency** для сессий (это временные данные с TTL 30 минут)
- **Компромисс**: Временная рассинхронизация (до восстановления узла)

**Read Repair:**

- **Когда**: При каждом чтении сессии (это частая операция - каждый HTTP request)
- **Преимущество**: Автоматическое исправление рассинхронизации в фоне при чтении
- **Компромисс**: Minimal - latency не страдает, т.к. восстановление идёт асинхронно
