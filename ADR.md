# Architecture Decision Record (ADR)

## Анализ шард-ключей для коллекций Black Friday

### 1. Коллекция `orders`

#### Атрибуты:

- `_id: ObjectId`
- `user_id: ObjectId`
- `items: { product_id: ObjectId, quantity: number, price: number }[]`
- `status: "active" | "ordered" | "abandoned"`
- `total: number`
- `geo_zone: string`
- `created_at: Date`

#### Кандидаты для шард-ключа:

**1. `geo_zone` (простой ключ)**

- **Преимущества:**
  - Распределение по географическим зонам
  - Отчётность и аналитика часто требуют данные по регионам
  - Хорошая кардинальность при достаточном количестве геозон
- **Недостатки:**
  - Потенциальная неравномерность нагрузки (Москва vs маленькие города)
  - При малом количестве зон - ограниченная масштабируемость

**2. `{ geo_zone: 1, user_id: 1 }` (составной ключ)**

- **Преимущества:**
  - Лучшая кардинальность за счёт комбинации полей
  - Эффективный поиск истории заказов конкретного пользователя
  - Сохраняется географическая локальность данных
  - Более равномерное распределение данных по шардам
- **Недостатки:**
  - Требует указания обоих полей в запросах для оптимальной производительности

**3. `user_id` (простой ключ, хешированный)**

- **Преимущества:**
  - Равномерное распределение данных
  - Быстрый поиск всех заказов пользователя
  - Простота использования
- **Недостатки:**
  - Полностью теряется географическая локальность

#### **Лучший кандидат:** `{ geo_zone: 1, user_id: 1 }`

---

### 2. Коллекция `products`

#### Атрибуты:

- `_id: ObjectId`
- `name: string`
- `category: string`
- `price: number`
- `amount_left: {geo_zone: string, amount: number}[]`
- `attributes: Object`

#### Кандидаты для шард-ключа:

**1. `category` (простой ключ)**

- **Преимущества:**
  - Естественная группировка данных
  - Эффективный поиск и фильтрация по категориям
  - Хорошо подходит для аналитики по категориям
- **Недостатки:**
  - Низкая кардинальность (ограниченное количество категорий)
  - Популярные категории ("Электроника") создадут hot-spot
  - Неравномерное распределение данных
  - Плохая масштабируемость

**2. `{ category: 1, _id: 1 }` (составной ключ)**

- **Преимущества:**
  - Высокая кардинальность за счёт добавления уникального \_id
  - Эффективный поиск по категориям
  - Равномерное распределение данных внутри категорий
  - Поддержка поиска конкретного товара по \_id с указанием категории
- **Недостатки:**
  - Поиск товара только по \_id потребует scatter-gather
  - Обновление остатков требует знания категории товара

**3. `_id` (простой ключ, хешированный)**

- **Преимущества:**
  - Максимально равномерное распределение
  - Быстрый доступ к конкретному товару по \_id
  - Хорошая масштабируемость
  - Простота реализации
- **Недостатки:**
  - Поиск по категориям всегда требует scatter-gather
  - Фильтрация по цене будет неэффективной
  - Нет географической локальности для обновления остатков

**4. `{ category: 1, price: 1 }` (составной ключ с range-полем)**

- **Преимущества:**
  - Оптимален для поиска по категориям с фильтрацией по цене
  - Эффективные range-запросы по цене внутри категории
- **Недостатки:**
  - Низкая общая кардинальность
  - Потенциальные hot-spots в популярных ценовых диапазонах
  - Изменение цены может потребовать миграции документа между шардами
  - Не рекомендуется использовать изменяемые поля в шард-ключе

#### **Лучший кандидат:** `{ category: 1, _id: 1 }`

Обеспечивает баланс между эффективным поиском по категориям и равномерным распределением данных.

Альтернатива: хешированный `_id` для максимальной производительности записи, если чтение по категориям менее критично.

### 3. Коллекция `carts`

#### Атрибуты:

- `_id: ObjectId`
- `user_id: ObjectId`
- `session_id: string`
- `items: { product_id: ObjectId, quantity: number }[]`
- `status: "active" | "ordered" | "abandoned"`
- `created_at: Date`
- `updated_at: Date`
- `expires_at: Date`

#### Кандидаты для шард-ключа:

**1. `session_id` (простой ключ, хешированный)**

- **Преимущества:**
  - Очень высокая кардинальность (уникальные сессии)
  - Равномерное распределение
  - Быстрый доступ к гостевым корзинам
  - Хорошая масштабируемость
- **Недостатки:**
  - Поиск корзины авторизованного пользователя по `user_id` требует scatter-gather
  - Операция слияния корзин может быть неэффективной
  - После авторизации пользователь чаще работает через `user_id`, а не `session_id`

**2. `user_id` (простой ключ, хешированный)**

- **Преимущества:**
  - Высокая кардинальность
  - Равномерное распределение
  - Эффективный поиск корзины авторизованного пользователя
  - Оптимально для постоянных клиентов
- **Недостатки:**
  - Гостевые корзины (без `user_id`) не могут использовать этот ключ
  - Требуется дополнительная логика для обработки гостей
  - Часть корзин может иметь null или временное значение `user_id`

**3. `_id` (простой ключ, хешированный)**

- **Преимущества:**
  - Максимально равномерное распределение
  - Простота реализации
  - Отличная масштабируемость
- **Недостатки:**
  - Поиск активной корзины по `user_id` или `session_id` всегда требует scatter-gather

**4. Гибридный подход: составной ключ `{ user_id: 1, session_id: 1 }`**

- **Преимущества:**
  - Покрывает оба сценария: авторизованные и гостевые корзины
  - Высокая кардинальность
  - Для авторизованных: поиск по `user_id`
  - Для гостей: поиск по `session_id`
- **Недостатки:**
  - Сложность реализации: нужно заполнять оба поля или использовать условную логику
  - Один из ключей часто будет null или пустым

#### **Лучший кандидат:**

Хешированный `user_id` для основной коллекции `carts`, где для гостевых корзин используется временный `user_id` (например, на основе `session_id`). При авторизации гостя происходит обновление `user_id` на реальный.

## Выбор стратегий шардирования

### 1. Коллекция `orders`

#### **Выбранная стратегия:** диапазонное шардирование

#### **Шард-ключ:** `{ geo_zone: 1, user_id: 1 }`

#### **Обоснование выбора:**

1. **Географическая локальность данных**

   - Заказы физически группируются по регионам
   - Списание остатков товаров происходит в рамках одной геозоны
   - Минимизируются межшардовые транзакции при оформлении заказа

   ```javascript
   // Создание заказа с списанием остатков
   // Все данные (заказ + остатки в геозоне) на одном или соседних шардах
   db.orders.insertOne({
     user_id: ObjectId("..."),
     geo_zone: "Moscow",
     items: [{ product_id: ObjectId("..."), quantity: 2 }],
   });

   // Обновление остатков в той же геозоне — локальная операция
   db.products.updateOne(
     { _id: product_id, "amount_left.geo_zone": "Moscow" },
     { $inc: { "amount_left.$.amount": -2 } }
   );
   ```

2. **Эффективные запросы для основных операций**

   **Операция 1: История заказов пользователя (15% трафика)**

   ```javascript
   // Targeted query — один шард
   db.orders.find({
     geo_zone: "Moscow",
     user_id: ObjectId("..."),
   });
   ```

   **Операция 2: Создание заказа (80% трафика)**

   ```javascript
   // Запись идёт точно в нужный шард
   db.orders.insertOne({
     geo_zone: "Moscow",      // ← Mongos сразу знает шард
     user_id: ObjectId("..."),
     items: [...],
     status: "active"
   })
   ```

   **Операция 3: Отчёты по геозоне (5% трафика)**

   ```javascript
   // Частичный scatter — только шарды одной геозоны
   db.orders.aggregate([
     { $match: { geo_zone: "Moscow" } },
     { $group: { _id: "$status", total: { $sum: "$total" } } },
   ]);
   ```

3. **Высокая кардинальность составного ключа**

   - `geo_zone`: 10-50 значений (основные города России)
   - `user_id`: миллионы значений
   - **Итоговая кардинальность**: очень высокая
   - Равномерное распределение внутри каждой геозоны

4. **Бизнес-логика Black Friday**
   - Пиковые нагрузки различаются по регионам (разные часовые пояса)
   - Москва: пик в 12:00 MSK → нагрузка на шарды Москвы
   - Владивосток: пик в 12:00 VLAT (9 часов разницы) → нагрузка на шарды Владивостока
   - **Естественное распределение нагрузки во времени**

---

#### **Почему не полное географическое распределение?**

**1. Межрегиональные операции**
Проблема: пользователь из Москвы покупает товар, но его остатки закончились в московской геозоне

При географическом распределении:

1. Запись заказа → Дата-центр Москвы (80ms latency внутри)
2. Списание остатков → Дата-центр СПб (150ms latency между городами!)
3. Обновление inventory → Дата-центр СПб (ещё 150ms)
   Итого: 380ms вместо 80ms

**2. Отсутствие строгой привязки пользователя к региону**
Пользователь из одного региона может делать заказ в другой.

**3. Высокие требования к инфраструктуре**

**4. Black Friday — это кратковременный пик**

Характеристики Black Friday:

- Длительность: 24-48 часов
- Основной пик: 00:00 - 06:00 (6 часов)
- Остальное время: обычная нагрузка

Географическое распределение оправдано для:

- Круглогодичной высокой нагрузки
- Строгих требований к latency (< 50ms)
- Юридических требований (хранение данных в регионе)

#### **Конфигурация шардирования:**

```javascript
// 1. Создание шардированной коллекции
sh.enableSharding("somedb");

// 2. Создание индекса для шард-ключа
db.orders.createIndex({ geo_zone: 1, user_id: 1 });

// 3. Шардирование коллекции
sh.shardCollection("somedb.orders", { geo_zone: 1, user_id: 1 });

// 4. Предварительное разделение на зоны (Zone Sharding)
// Распределяем геозоны по шардам для контроля

// Москва и область → Shard 0, 1
sh.addShardToZone("shard0", "moscow-zone");
sh.addShardToZone("shard1", "moscow-zone");
sh.updateZoneKeyRange(
  "somedb.orders",
  { geo_zone: "Moscow", user_id: MinKey },
  { geo_zone: "Moscow", user_id: MaxKey },
  "moscow-zone"
);

// Санкт-Петербург → Shard 2
sh.addShardToZone("shard2", "spb-zone");
sh.updateZoneKeyRange(
  "somedb.orders",
  { geo_zone: "SPB", user_id: MinKey },
  { geo_zone: "SPB", user_id: MaxKey },
  "spb-zone"
);

// Остальные регионы → Shard 3, 4
sh.addShardToZone("shard3", "other-zone");
sh.addShardToZone("shard4", "other-zone");
```

### 2. Коллекция `products`

#### **Выбранная стратегия:** диапазонное шардирование

#### **Шард-ключ:** `{ category: 1, _id: 1 }`

#### **Обоснование выбора:**

1. **Основной паттерн использования — поиск по категориям**

   **Операция 1: Каталог товаров**

   ```javascript
   // Targeted query — только шарды с данной категорией
   db.products
     .find({
       category: "Electronics",
       price: { $gte: 10000, $lte: 50000 },
     })
     .sort({ price: 1 });

   // Mongos направляет запрос только на шарды с "Electronics"
   // Например: Shard 1 и Shard 2 (если категория распределена на 2 шарда)
   ```

2. **Равномерное распределение через \_id**

   - Проблема: категорий мало (~20-50), популярные категории создадут hot-spots
   - Решение: добавление `_id` как второй части ключа
   - Внутри каждой категории товары равномерно распределяются по ObjectId

   ```javascript
   // Распределение товаров категории "Electronics"
   Shard 1: { category: "Electronics", _id: ObjectId("507f1f...") ... ObjectId("607f1f...") }
   Shard 2: { category: "Electronics", _id: ObjectId("607f1f...") ... ObjectId("707f1f...") }
   Shard 3: { category: "Electronics", _id: ObjectId("707f1f...") ... ObjectId("807f1f...") }

   // Категория "Books" может быть меньше
   Shard 4: { category: "Books", _id: ObjectId("507f1f...") ... ObjectId("807f1f...") }
   ```

3. **Эффективное обновление остатков**

   **Операция 2: Списание товара**

   ```javascript
   // Если знаем category и _id — прямое попадание в один шард
   db.products.updateOne(
     {
       category: "Electronics", // ← из кеша или контекста заказа
       _id: ObjectId("507f1f77bcf86cd799439011"),
     },
     {
       $inc: { "amount_left.$[elem].amount": -1 },
     },
     {
       arrayFilters: [{ "elem.geo_zone": "Moscow" }],
     }
   );
   ```

4. **Изоляция нагрузки по категориям**

#### **Конфигурация шардирования:**

```javascript
// 1. Создание индекса
db.products.createIndex({ category: 1, _id: 1 });

// 2. Шардирование
sh.shardCollection("somedb.products", { category: 1, _id: 1 });

// 3. Опционально: Zone Sharding для контроля популярных категорий
// Выделяем больше шардов для "Электроники"
sh.addShardToZone("shard0", "electronics-zone");
sh.addShardToZone("shard1", "electronics-zone");
sh.addShardToZone("shard2", "electronics-zone");

sh.updateZoneKeyRange(
  "somedb.products",
  { category: "Electronics", _id: MinKey },
  { category: "Electronics", _id: MaxKey },
  "electronics-zone"
);

// Остальные категории на других шардах
sh.addShardToZone("shard3", "other-categories");
sh.addShardToZone("shard4", "other-categories");
```

### 3. Коллекция `carts`

#### **Выбранная стратегия:** хэшированное шардирование

#### **Шард-ключ:** `user_id` (hashed)

#### **Обоснование выбора:**

1. **Максимально равномерное распределение нагрузки**

   **Black Friday характеристика:**

   - Огромное количество одновременных пользователей
   - Постоянные обновления корзин

2. **Эффективные операции с корзиной**

   **Операция 1: Получить активную корзину**

   ```javascript
   db.carts.findOne({
     user_id: ObjectId("507f1f77bcf86cd799439011"),
     status: "active",
   });

   // Hash(user_id) → Shard 2
   // Запрос идёт напрямую на Shard 2
   ```

   **Операция 2: Добавить товар в корзину**

   ```javascript
   // Targeted update — один шард
   db.carts.updateOne(
     {
       user_id: ObjectId("507f1f77bcf86cd799439011"),
       status: "active",
     },
     {
       $push: {
         items: { product_id: ObjectId("..."), quantity: 1 },
       },
       $set: { updated_at: new Date() },
     }
   );
   ```

   **Операция 3: Создать корзину**

   ```javascript
   // Запись в случайный шард
   db.carts.insertOne({
     user_id: ObjectId("..."), // Хешируется → любой шард
     session_id: "abc123",
     items: [],
     status: "active",
     created_at: new Date(),
   });
   ```

3. **Решение проблемы гостевых корзин**

   ```javascript
   // Для гостей: генерируем временный user_id из session_id
   function getCartUserId(sessionId, realUserId) {
     if (realUserId) {
       return realUserId; // Авторизованный пользователь
     }
     // Гость: создаём стабильный ObjectId из session_id
     return ObjectId(
       crypto.createHash("md5").update(sessionId).digest("hex").substring(0, 24)
     );
   }

   // Создание гостевой корзины
   const guestUserId = getCartUserId(sessionId, null);
   db.carts.insertOne({
     user_id: guestUserId, // Временный, но стабильный
     session_id: sessionId,
     items: [{ product_id: ObjectId("..."), quantity: 1 }],
     status: "active",
     is_guest: true,
   });

   // При авторизации: обновляем user_id
   ```

4. **Автоматическая очистка старых корзин**

   ```javascript
   // TTL индекс для автоматического удаления
   db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 });

   // При создании корзины
   db.carts.insertOne({
     user_id: ObjectId("..."),
     items: [],
     status: "active",
     created_at: new Date(),
     expires_at: new Date(Date.now() + 7 * 24 * 60 * 60 * 1000), // 7 дней
   });

   // MongoDB автоматически удалит через 7 дней
   // Работает на каждом шарде независимо
   ```

5. **Отсутствие hot-spots при пиковых нагрузках**
   - VIP-клиенты с большими корзинами
   - Боты и скрипты
   - Влиятельные пользователи
   - **Все равномерно распределены по хешу**

#### **Конфигурация шардирования:**

```javascript
// 1. Создание хешированного индекса
db.carts.createIndex({ user_id: "hashed" });

// 2. Шардирование с хешированием
sh.shardCollection("somedb.carts", { user_id: "hashed" });
```
